# T-017 — Controlar migrações incrementais do banco

**Tipo** — Implementação

**Execução** — Verificada

**Data de execução** — 2026-11-12

**Aceite manual** — Pendente

## Alteração e limites

Preparar o controle de migrações SQL incrementais, integrá-lo ao CD automatizado e documentar seu uso em desenvolvimento e produção, preservando os dados e o schema atual. Esta task especifica a entrega; sua criação não constitui execução ou aceite da implementação.

Referências: [Configuração e banco](../arquitetura/Persistencia-e-Compatibilidade.md#configuração-e-banco), [GitHub Actions e webhook do aaPanel](../arquitetura/Persistencia-e-Compatibilidade.md#github-actions-e-webhook-do-aapanel), [Desenvolvimento e verificações isoladas](../arquitetura/Persistencia-e-Compatibilidade.md#desenvolvimento-e-verificações-isoladas), [README](../../README.md#configurar-e-abrir) e [política de validação](../arquitetura/Qualidade-e-Desempenho.md#validação-proporcional-à-alteração).

Hoje, `server/db.ts` executa integralmente `server/schema.sql` em uma transação com lock. O SQL cria os objetos com `IF NOT EXISTS` e registra a versão 1 em `ecovit_migrations`, mas o executor não consulta esse histórico para selecionar alterações pendentes. O setup local compara os objetos existentes com o schema de referência antes de migrar. O deploy do aaPanel compila e reinicia a API, sem executar migrações.

### Escopo

- Manter uma sequência explícita e ordenada de migrações SQL no repositório, sem biblioteca ou serviço adicional. Consultar `ecovit_migrations` para aplicar somente versões pendentes, sem reaplicar ou editar versões já entregues. Alterações futuras recebem novas versões.
- Preservar a versão inicial 1 e os registros existentes, inclusive suas datas. Uma instalação nova deve chegar à mesma estrutura atual; um banco atual já migrado não deve ter tabelas recriadas, dados regravados ou histórico reiniciado.
- Reutilizar a tabela de controle existente, sem acrescentar colunas, tabelas, índices ou outras alterações ao schema entregue. Não incluir migração funcional de versão 2 nesta task. Migrações adicionais usadas para verificar o executor pertencem exclusivamente a testes isolados.
- Serializar execuções concorrentes antes de consultar e aplicar pendências. Aplicar cada migração e seu registro de versão na mesma transação; falha não pode deixar aquela versão parcialmente aplicada ou marcada como concluída. Migrações anteriores concluídas permanecem registradas para retomada.
- Rejeitar versões duplicadas, sequência inválida, histórico inconsistente ou versão do banco desconhecida pelo código, com diagnóstico acionável antes de aplicar novas alterações. Não adotar silenciosamente um banco preexistente sem histórico como se fosse instalação nova; distinguir esse conflito do banco vazio.
- Manter `db:migrate` e a entrada compilada da CLI como caminhos administrativos, usando `DATABASE_MIGRATION_URL` com a role proprietária, configurada no `.env` privado existente. Preservar `DATABASE_URL` para execução da API e manter segredos fora dos logs. Somente o comando de migração deve selecionar a conexão proprietária para acessar o PostgreSQL.
- Compatibilizar o setup local e os consumidores de migração dos testes com o executor incremental. Preservar a recusa de recursos incompatíveis, a proteção do `.env` e a geração/preservação de credenciais. A comparação do setup não pode impedir uma atualização suportada apenas por encontrar uma versão anterior válida.
- Incluir os arquivos necessários no build do servidor, permitindo executar a mesma sequência pela CLI em código-fonte e pelo pacote compilado.
- Definir na documentação como cada migração futura entrega as permissões necessárias à role da API para objetos novos, preservando a separação entre proprietário e execução e a restrição de acesso à tabela de migrações. A reaplicação do setup local não deve ser requisito para migrar.

### Integração com o CD automatizado

- Integrar a execução da CLI compilada de migração ao script de deploy do aaPanel, usando os artefatos da mesma revisão aprovada pelo CI. Executar após a compilação bem-sucedida e antes de `pm2 restart ecovit`, dentro do lock existente de implantação. Sem pendências, prosseguir normalmente.
- Exigir sucesso da migração para reiniciar a API e concluir a publicação. Falha de migração, de leitura da credencial ou de autenticação deve encerrar o deploy com código diferente de zero, sem reiniciar a API, emitir novo recibo de sucesso ou registrar `ECOVIT_DEPLOY_OK`. Nunca recorrer à conexão da role de execução quando a credencial de migração estiver indisponível.
- Fazer a falha impedir o sucesso do workflow do GitHub, preservando a exigência de recibo da própria tentativa e a verificação de saúde. A aceitação HTTP do webhook não comprova sucesso da migração ou do deploy. Os diagnósticos devem indicar a etapa que falhou sem revelar segredos.
- Disponibilizar `DATABASE_MIGRATION_URL` no mesmo `.env` privado já usado pela aplicação, sem exigir outro arquivo de configuração. A CLI de migração deve carregar esse arquivo e exigir uma conexão proprietária válida. Manter o `.env` ignorado pelo Git, fora da raiz pública e com permissões restritas ao usuário responsável, conforme o contrato de implantação. Não carregar o arquivo por execução de comandos de shell nem exportar seu conteúdo globalmente no deploy ou cadastrá-lo no ambiente do PM2. Não incluir segredos em argumentos de linha de comando, logs, recibos, Git ou payload do webhook. Documentar preenchimento e atualização da variável sem valores reais. Como a API também carrega o `.env`, a variável pode estar disponível em seu ambiente; isso não constitui isolamento da credencial. A API deve continuar conectando exclusivamente por `DATABASE_URL`, sem usar a conexão proprietária. Não prometer isolamento entre processos que executam com o mesmo usuário Linux.
- Preservar os limites do deploy atual: o checkout e os arquivos estáticos são atualizados antes do reinício e não há reversão automática. Interromper o deploy não restaura esses arquivos nem desfaz migrações anteriores concluídas. Documentar essa condição, sem declarar publicação atômica ou disponibilidade contínua e sem introduzir outra infraestrutura de deploy nesta task.
- Como a API anterior permanece em execução durante a migração, migrações do fluxo automático devem ser compatíveis com essa versão. Documentar evolução em etapas compatíveis e o procedimento de manutenção para mudanças incompatíveis, coordenando o bloqueio do CD antes de integrar/publicar a revisão correspondente. Não executar automaticamente uma alteração incompatível apenas porque antecede o reinício.

### Procedimento a documentar

Atualizar o assunto responsável na arquitetura e o roteiro operacional do README, com referências entre eles, distinguindo implementação de comportamento já disponível:

- **Desenvolvimento:** criar uma nova migração sem editar as anteriores, verificar criação e atualização com dados em banco isolado, configurar `DATABASE_MIGRATION_URL` no `.env` privado existente, executar o comando de migração, conferir versão e permissões e iniciar a aplicação correspondente. Distinguir instalação inicial, atualização do banco dev e preparação dos testes. Não apagar/recriar o banco como procedimento de atualização.
- **Produção:** confirmar backup recuperável com o administrador, preencher `DATABASE_MIGRATION_URL` no `.env` privado existente e publicar a revisão aprovada pelo CD. Descrever a sequência compilação → migração → reinício → saúde/recibo, a conferência do histórico/permissões e das operações afetadas e o comportamento quando não houver pendências. Fornecer também o comando da CLI compilada para intervenção administrativa e retomada, carregando a mesma configuração. Explicar a coordenação de manutenção e bloqueio do CD para alterações incompatíveis. Atualizar a orientação anterior da arquitetura sobre credencial exclusivamente temporária para refletir sua permanência no `.env`, sem afirmar isolamento do ambiente da API.
- **Falhas e mudanças incompatíveis:** explicar retomada de pendências, preservação das migrações já concluídas, etapas compatíveis entre versões ou janela de manutenção e diferença entre voltar o código e restaurar o banco. Não prometer reversão automática de migração concluída.

Não alterar o schema funcional, os formatos de documentos/projetos ou as regras do produto. Não executar migrações no banco do aplicativo ou em produção nesta entrega. A automação fica na etapa de deploy do webhook, sem migração automática no startup da API ou nas requisições. Implementar e verificar a integração em ambiente isolado e documentar sua ativação; não configurar backups, credenciais ou serviços nem acionar publicação no servidor nesta entrega.

## Critérios de aceite

- [x] **A01** — Banco vazio isolado recebe a versão inicial e a mesma estrutura atual. Banco atual com versão 1 e dados representativos preserva estrutura, registros e data original da migração; uma segunda execução não reaplica versões concluídas.
- [x] **A02** — Com migrações sintéticas exclusivas dos testes, o executor aplica pendências em ordem, registra cada versão somente junto de seu sucesso e retoma após falha sem duplicar efeitos anteriores. Execuções concorrentes não aplicam a mesma versão duas vezes.
- [x] **A03** — Versões duplicadas, sequência inválida, histórico inconsistente, banco com versão desconhecida e objetos preexistentes sem histórico são recusados com diagnóstico, sem novas alterações persistidas. Banco vazio permanece suportado.
- [x] **A04** — Setup local, CLI administrativa e consumidores dos testes usam o controle incremental sem perder as proteções existentes. Atualizações suportadas não são bloqueadas pela comparação prematura com a estrutura final; conflitos reais continuam sendo recusados. A role de execução mantém suas restrições e a orientação para permissões de objetos novos é explícita.
- [x] **A05** — O build contém os recursos SQL necessários e a CLI compilada executa a mesma sequência e respeita o mesmo histórico da CLI em código-fonte. Ambas carregam `DATABASE_MIGRATION_URL` do `.env` privado existente, sem exigir outro arquivo e sem divulgar a credencial nos logs.
- [x] **A06** — README e arquitetura descrevem procedimentos executáveis de dev e prod, incluindo histórico, permissões, backup, configuração protegida da credencial, sequência do CD e recuperação de falhas. Distinguem o setup de provisionamento da migração de atualização, a nova automação do deploy anterior e as etapas de ativação no servidor. Explicitam compatibilidade com a API anterior, manutenção para mudanças incompatíveis e ausência de reversão automática dos arquivos ou de migrações concluídas.
- [x] **A07** — O diff não introduz versão funcional além da 1 nem altera a estrutura SQL atual. Verificações de banco usam somente ambiente isolado; o banco do aplicativo, a porta 5173 e a produção permanecem sem intervenção.
- [x] **A08** — Em verificação isolada do deploy, a migração usa a CLI compilada da revisão aprovada, após o build e antes do reinício, sob o lock existente. Sucesso e ausência de pendências permitem reinício e verificações finais; falha de migração impede reinício, novo recibo e mensagem de sucesso, encerra com erro e não permite sucesso do workflow por HTTP 2xx ou recibo de tentativa anterior.
- [x] **A09** — `.env` ilegível ou `DATABASE_MIGRATION_URL` ausente, vazia ou inválida interrompe o deploy sem usar `DATABASE_URL` como alternativa. Com credencial válida no `.env` existente, a migração usa a role proprietária e a API continua usando exclusivamente `DATABASE_URL`. O deploy não executa o conteúdo do `.env` como shell nem exporta seus segredos globalmente para build/PM2. O arquivo permanece privado, ignorado pelo Git e fora da raiz pública; o segredo não aparece em argumentos, logs, recibos ou payloads. A documentação reconhece que o carregamento compartilhado do `.env` permite acesso à variável pelo processo da API. Verificação com valores sintéticos, sem acessar segredos de produção.
